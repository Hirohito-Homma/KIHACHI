# ADR-0008: stem分離の境界

**Status:** Accepted
**Date:** 2026-08-15

## Context

v0.1は2つの問いを未解明のまま締めた。どちらも完成ミックスしか測れないことに由来する。

- コード進行が測れない。29テイク中18テイクで一致率0.0、残りも最大0.167。原因がマスキングなのか、
  モデルが進行を弾いていないのかを区別できない。検出器は健全で、合成した進行なら一致率1.0を返す。
- 低域偏重がKIHACHIの指定由来かモデルの癖か分からない。

どちらもstemがあれば測れる。ベースとハーモニーが分かれていれば、chroma検出器は今日と同じ精度で
働くはずである（クリーンな信号では24/24正解する）。

一方でstem分離器（Demucs等）はtorchと数百MBの重みを要求する。これをコアへ入れると
ADR-0001の「コアは標準ライブラリだけで動く」が壊れる。現在`dependencies = []`である。

## Decision

**分離器を実行しない。**KIHACHIは分離の**契約**だけを持つ。

- `stems prepare` は実行すべきコマンドを表示する。実行しない。
- `stems import` は、どこで生成されたかを問わずstemファイルを検証し、`stem_manifest.json` へ記録する。
- 分離済みstemは通常のWAVなので、`analyze --audio` がそのまま使える。新しい解析経路は作らない。

これは既存の2つのパターンの合成である。ACE-Stepアダプター（ADR-0002）が
「モデル本体・GPU・サーバー生存をコアへ持ち込まない」としたのと同じ理由で、
`instrumental-plan` が「repaintコマンドは表示するだけで実行しない」としたのと同じ形を取る。
後者の理由もそのまま当てはまる — 分離はGPUと数分を使い、既存ファイルを上書きしうる。

契約は次の通り。

| 項目 | 規定 |
|---|---|
| 既定モデル | `htdemucs`（4 stem: drums / bass / other / vocals） |
| 配置 | `<project>/audio/stems/<stem>.wav` |
| 検証 | 全stemが存在し、sample rate・channel数・尺が元Audioと一致すること |
| 記録 | `stem_manifest.json` に元AudioのSHA-256、各stemのSHA-256、モデル名、尺 |
| 非破壊 | 元Audioは読むだけ。`--overwrite` なしにmanifestを置換しない |

## Options Considered

### A. コマンドを表示し、成果物を取り込む（採用）

| Dimension | Assessment |
|---|---|
| 依存 | ゼロのまま |
| 実行場所 | ローカルCPUでもvast.aiでも、呼び出し側が選べる |
| テスト容易性 | 高い（合成WAVで検証できる、GPU不要） |
| 手間 | 利用者が1コマンド手で走らせる |

### B. demucsをoptional dependencyにしてsubprocess実行

| Dimension | Assessment |
|---|---|
| 依存 | torch + 重み数百MB（optionalでも実質必須になる） |
| 実行場所 | ローカルに固定される |
| テスト容易性 | CIで分離を走らせられない |
| 手間 | 少ない |

### C. 分離器をRESTサービス化してアダプターを書く

| Dimension | Assessment |
|---|---|
| 依存 | ゼロだがサーバー実装が要る |
| 実行場所 | リモート固定 |
| テスト容易性 | 高い |
| 手間 | v0.2の最初の一歩としては重い |

Cは将来Aの上に足せる。契約（配置とmanifest）が同じなら、取り込み口が変わるだけである。

## Consequences

- 分離器を入れずに、stem対応の解析・テスト・CIが動く。
- 利用者は分離コマンドを自分で1回走らせる必要がある。`stems prepare` がそれを表示する。
- stemの品質はKIHACHIの管理外になる。モデル名と尺はmanifestに残るので、後から出所は追える。
- v0.1の2つの問いは、stemを取り込んだ時点で測定可能になる。答えが出るとは限らない —
  分離自体が完全ではないため、否定的な結果の解釈には注意が要る。
