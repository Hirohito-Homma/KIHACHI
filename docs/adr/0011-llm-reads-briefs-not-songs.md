# ADR-0011: LLMはブリーフを読む。曲は書かない

**Status:** Accepted
**Date:** 2026-08-16

## Context

v0.2の残りはLLM接続である。「Music Brainのルールベース部分をLLMで置き換える」と読むのが
自然だが、置き換える前に**何が足りないのか**を測った。

`example_output`の33プロジェクトが持つ6種類のブリーフに、現在の解釈器を当てた結果:

| ブリーフ | 反応したtrait |
|---|---|
| Mutation Funk系（5種） | 1〜6 |
| **アンビエント系（1種、85文字）** | **0** |

語彙は**9 trait / 34表現**しかない。反応しなかったブリーフはこれである。

```
アンビエント。110 BPM、D#m。2分程度。きらびやかで高域中心、繊細。
ベースは控えめで薄い。パーカッションは軽く、シェイカーとハイハット中心。インストゥルメンタル。
```

BPM・キー・尺・ジャンル名は正規表現とジャンル照合が拾う。しかし
**「きらびやかで高域中心」「繊細」「ベースは控えめで薄い」「パーカッションは軽く」は
一語も届かない。**SongSpecは`darkness 0.48`というジャンル既定値のまま出た
（`bright-contrast-01`、`-02-pure`）。

同種の欠落はもう1つある。`_total_bars`は`分`しか読まないので、
**「32小節」「16 bars」と書いても読まれない**。既定の32小節に落ちるだけである。

**足りないのは作曲能力ではなく、理解の幅である。**そしてブリーフは、
理解されなかったことを**黙って**捨てられる。

一方、LLMを作曲経路へ入れることには具体的な障害がある。

| 制約 | 帰結 |
|---|---|
| 決定性が3層で固定（SongSpecのSHA-256、スキーマ、**MIDIバイト列**） | 作曲経路にLLMを入れると3つとも壊れる |
| `dependencies = []`（ADR-0001） | コアにHTTPクライアントもSDKも置けない |
| MIDIはLive上で56小節中56小節一致（ADR-0010） | **唯一設計を保持している経路**であり、確率的な生成に置き換える理由がない |

## Decision

**LLMは曲を書かない。ブリーフを既存の語彙へ翻訳し、翻訳できなかった部分を名指しする。**

ACE-Stepアダプター（ADR-0002）およびstem分離（ADR-0008）と同じ形を取る —
成果物を出し、適用は別の明示的な行為に残す。

```
brief ──LLM──▶ intent_reading.json ──▶ compose --intent
                    ├ traits:   既存のtrait名・polarity・strength・根拠となる原文
                    └ unmapped: 表現できなかった語句
```

契約は次の通り。

| 項目 | 規定 |
|---|---|
| 出力できるtrait名 | `intent.TRAIT_WORDS`にあるものだけ。外れた名前は**文書ごと拒否**する |
| 根拠 | 各traitはブリーフ中の実際の語句を引用する。引用が原文に無ければ拒否 |
| 決定性 | 成果物にブリーフのSHA-256とモデル名を記録する。**同じ成果物＋同じseedなら同じ曲**であり、golden testは生き残る |
| APIキー | 環境変数からのみ読む。リクエストにも成果物にもCLI出力にも残さない（ADR-0002と同じ） |
| 適用 | `compose --intent`が明示的に読む。LLMを呼ぶだけでは何も作らない |

**`unmapped`がこの機能の主目的である。**今日のアンビエント・ブリーフに対して、
現状は「何も起きなかった」ことすら出力されない。翻訳できない語句を名指しすれば、
語彙を広げるべき場所が分かる。

## Options Considered

### A. ブリーフを既存語彙へ翻訳し、残りを名指しする（採用）

| Dimension | Assessment |
|---|---|
| 決定性 | 保たれる（成果物が入力になる） |
| コアの依存 | ゼロのまま（アダプターは`adapters/`、stdlibの`urllib`） |
| 誤りの代償 | 小さい。成果物は人が読んで直せる |
| 効果 | 測った欠落にそのまま当たる |

### B. LLMがSongSpecを直接書く

| Dimension | Assessment |
|---|---|
| 決定性 | **壊れる**。3層の固定が全部無効になる |
| 誤りの代償 | 大きい。SongSpecはLive上で56/56を保っている唯一の設計である |
| 効果 | 作曲能力は不足していない |

### C. LLMがACE-Stepのプロンプトを書く

測定済みの理由で却下する。**指示は正しく送られて守られない**（進行一致率0.0、
低域偏重は指定を反転しても不変）。プロンプトの書き方を変えても結果は動かない。

### D. LLMがテイクを選ぶ

`shortlist`と`review-samples`の測定が示したのは、判別できる次元は測れば足り、
残りは**聴かないと決められない**ということである。LLMは聴けない。

## Consequences

- 語彙の限界が**出力に現れる**ようになる。今は黙って落ちている。
- LLMを呼ばなくてもKIHACHIは従来どおり動く。`--intent`は任意である。
- `unmapped`が空でないブリーフは、**語彙を広げる候補**として蓄積される。
  LLMに毎回同じ翻訳をさせるより、頻出する語をルール側へ昇格させるほうが安い。
- 段階を分ける。**未対応語句の検出はLLM無しで実装できる**（決定的でテストできる）。
  アダプターはその後で`unmapped`を埋める。
- LLMの出力を検証する手段は、引用がブリーフに実在するかの照合しかない。
  「その解釈が音楽的に妥当か」は測れない。ADR-0005以来と同じで、測定は判断を助けても代行しない。
