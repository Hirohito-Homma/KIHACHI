# ADR-0010: レンダーを曲ではなく素材として扱う

**Status:** Accepted
**Date:** 2026-08-16

## Context

v0.1以降の測定は、一貫して同じ形を示している。**生成器が壊すのは時間をまたぐ設計だけ**である。

| 測定 | 結果 |
|---|---|
| コード進行の一致（完成ミックス） | 29テイク中18テイクで0.0、最大0.167 |
| 指定を反転させた対照テイク4本 | drums+bassは9割から動かない |
| tail guardの充足（同一設計・seed違い5本） | 4本がblocking、不足2.14〜3.82s |
| 整合スコアの振れ（seedのみ変更、5本） | 37.32〜77.52 |
| MIDIの進行（Live上で読み戻し） | **56小節中56小節一致** |

短い時間スケールの音色や質感は問題ない。壊れるのは、進行・セクション・尺という
**時間をまたぐ約束**である。そしてMIDIはそれを完全に運ぶ。

同じ失敗が、素材として使う場合には性質を変えることも重要である。

| 失敗 | 曲として | 素材として |
|---|---|---|
| キー・進行が違う | 修正不能 | **移調では直らない**（下記の訂正を参照） |
| 低域偏重 | 修正不能 | stem分離済みの素材として使える |
| tailが届かない | 毎回賭け | 端を使わなければ無関係 |
| seedで大きく振れる | 原因の切り分け不能 | 単に採否の問題 |

### 訂正: 「移調で直る」は測定に支えられていません

この文書の初稿は「キーが違えば移調で直る」を採用の根拠の1つに挙げていました。
2026-08-16に測ったところ、**移調先が決まらない**ことが分かりました。

同一設計・seed違いの5テイクから中央4小節を切り出し、キーを推定した結果:

| 素材 | 確信度の範囲 | 前後半のプロファイル相関（中央値） | 中心ドリフト（最大） |
|---|---|---|---|
| 完成ミックスから | 0.049〜0.148 | 0.751 | 1.07半音 |
| ベースstemから | 0.054〜0.219 | 0.672 | 2.14半音 |

**確信度の閾値は0.25で、10本すべてが下回りました。**設計は全部D# minorですが、推定は
F# minor / D# minor / G# major / C# major とばらばらです。単音のベースstemなら素性が出ると
考えて測りましたが、三和音前提の推定器を単音へ当てているため改善せず、ドリフトはむしろ悪化しました。

ピッチ内容そのものは安定しています（相関0.75、ドリフト1半音程度）。つまり素材として使えないのでは
なく、**何から何へ移調すべきかが決められない**のです。

したがって当初の結論は「音程を持たない素材に限る」だった。**その後、原因は音声ではなく
推定器の側にあることが分かった。**

### 続報: 単音法なら根音は読めます（ただし調ではありません）

同日、単音向けの推定器（YINの累積平均正規化差分、`pitch.py`）を実装して同じベースstemに
当てた。同じ音声である。

| take | 推定root | agreement | 2位 |
|---|---|---|---|
| roll-101 | **D#** | 0.747 | D 0.09 |
| roll-102 | **D#** | 0.658 | G# 0.27 |
| roll-103 | **D#** | 0.444 | G# 0.26 |
| roll-104 | G# | 0.350 | **D# 0.31**（ほぼ同着） |
| roll-105 | G# | 0.551 | F# 0.18 |

設計はD# minorである。**5本中3本で設計の主音が首位**、1本はほぼ同着。三和音前提の推定器が
同じ音声に対して何とも一致しなかったのと対照的である。G#はD# minorの4度で、調外ではなく別の和音である。

合成音での検証: 55〜110 Hzで誤差10セント未満、第2倍音が基音の5倍でもオクターブ誤りなし、
無音は正しくunvoiced。

**それでも自動移調の根拠にはならない。**

- 可聴frame（-40 dBFS超）に対する検出率は**61%**（テイクごとに48〜93%）。無音の休符を
  正しく捨てている分と、大きい音を取りこぼしている分の両方が含まれる。
- agreementは0.35〜0.75で、2本は0.5を下回る。
- **rootは調ではない。**長短も、D#とG#のどちらが主音かも、単音線からは決まらない。

現時点の適用範囲:

- **音程を持たない素材** — そのまま使える。stem比でドラムが最大（57.9〜80.6%）。
- **音程を持つ素材** — 根音の候補は出せる。移調の判断材料にはなるが、**自動採用の根拠にはならない**。
  ADR-0005以来の形と同じで、測定は人の判断を助けるが代行しない。

## Decision

**ACE-Stepの出力を曲の完成品ではなく素材として扱う。**曲の構造はMIDIが運び、
生成器は音色と質感を供給する。

**短く焼くのではなく、中くらいに焼いて中央を切り出す。**2小節を要求することは、
生成器が最も苦手な領域（尺の端）へまっすぐ入ることを意味する。32小節でも
自分のグリッドに2.32s届かず、56小節でも5 seed中4 seedで足りなかった。
16〜32小節を焼いてその中央から切り出せば、冒頭の立ち上がりと、guardが届かない末尾の
両方を避けられる。

切り出しの契約は次の通り。

| 項目 | 規定 |
|---|---|
| 窓 | SongSpecの小節グリッド上。1始まり、終端は排他的 |
| 端 | 各端を最寄りのゼロ交差へスナップ。交差ペアのうち**ゼロに近い方**を選ぶ |
| スナップ上限 | 10 ms（110 BPMで1小節の0.5%）。届かない端はフェードし、その旨を記録する |
| 配置 | `<project>/audio/samples/<name>.wav` |
| 非破壊 | レンダーは読むだけ。モデルの挙動の証拠として残す |
| 素性 | プロジェクト、元AudioのSHA-256、seed、task_id、切り出した小節 |

**キーとBPMは「指定した値」として記録する。**測定値ではない。生成器がキーに従わないことは
測定済みなので、素材のメタデータがそれを保証しているかのように書くことはできない。

## Options Considered

### A. 中くらいに焼いて中央を切り出す（採用）

| Dimension | Assessment |
|---|---|
| tail guardの問題 | 触れずに済む |
| 冒頭の不安定さ | 避けられる |
| GPU時間 | 1テイク24秒（56小節、turbo）。使わない部分も焼く |
| 追加実装 | スライサーと素性の記録 |

### B. 2〜4小節を直接焼く

| Dimension | Assessment |
|---|---|
| tail guardの問題 | **最悪化する**（不足はほぼ一定なので、短いほど割合が大きい） |
| 冒頭の不安定さ | 素材の大部分を占める |
| GPU時間 | 短い |
| 追加実装 | 少ない |

### C. 曲として焼き続け、失敗テイクを捨てる

現状である。`shortlist`が選別を助けるが、進行・キー・構造は依然として設計どおりにならず、
選別で救えるのは「たまたま良かったテイク」だけである。

## 実測: 曲として全滅したレンダーから、素材は取れます

2026-08-16に32小節・seed違い3本を焼きました。32小節は「tail guardが届かない」と
記録している当のケースです。

| take | 曲として | 中央4小節（9:13）を切ると |
|---|---|---|
| roll-201 | **blocking**（末尾無音2.58s） | **clean**（最大跳躍0.031） |
| roll-202 | **blocking** + discontinuity | warning（`silent_gap`） |
| roll-203 | **blocking**（末尾無音2.58s） | **clean**（最大跳躍0.472） |

**3本とも曲としては使えず、2本は素材として無傷でした。**

roll-202のサンプルが持つ無音は、レンダー最大の無音（32.36秒）とは**別の小さいもの**です。
レンダー側の検査はコードごとに最悪1点しか位置を記録しないため、`known_defects_inside`は
これを検出しません。**切り出した後にサンプル自体を検査する**という規則が、ここで実際に効きました。

## Consequences

- 曲の構造はMIDI経路が担う。Live展開（ADR未採番、2026-08-16に実機確認）が本線になる。
- 生成器への要求が変わる。「この設計どおりの曲」ではなく「この質感の数小節」になり、
  進行やセクションの指示が通らないことは問題でなくなる。
- **`shortlist`の4次元は素材の選別に使えない。**duration・tempo・section_boundaries・
  section_energyはいずれもアレンジの整合を測るもので、4小節のループには意味がない。
  素材用の指標は別に測り直した（`material.py`）。13本の実測で唯一「良し悪し」が定義できたのは
  **グリッド整合**（0.095〜0.935）で、これだけを採点する。密度・レベル・明るさは向きが
  決められないので報告のみ。打点が12未満なら`undetermined`と答える — 持続音は9打点から
  1.000を返し、それは整合ではない。
- 素材をLiveへ持ち込む経路が要る。`import_vocal_take`がそれに当たる。この文書を書いた
  時点でAbletonGPTの`import-kihachi`はこの操作を受け付けておらず、設計の前提条件として
  挙げていた。**AbletonGPT0.2#137で解消済み**（`set_clip_parameter_envelope`も同時に追加）。
  ただしジョブ経路経由での実機適用はまだ確認していない。
- 中央を切り出せば端の問題は避けられるが、**素材が元から持つ不連続は引き継ぐ**。
  実際に切り出した4小節は、カットが作ったものではない`discontinuity` warningを含んでいた。
  切り出し後も`scan_material`で測ること。
